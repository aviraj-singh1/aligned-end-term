# Database foundation: development and verification

This is Phase 1 of [the implementation plan](AUTH_DATABASE_IMPLEMENTATION_PLAN.md).
SQLModel table definitions, PostgreSQL configuration and Alembic migrations are
separate from the existing reconciliation dataclasses and routes. No authentication,
workspace API, team management or UI is enabled by this foundation alone.

## Models and ownership

`backend/app/db/models/` defines users, external auth identities, Individual/Firm
workspaces, memberships, invites, clients, GST registrations, assignments, run
metadata and audit events. Both workspace types use the same client tables.

Composite foreign keys prevent cross-workspace client assignments, registrations,
run links and audit references. They **do not authorize reads**. Firm-only team
features, Individual single-member policy, last-admin protection and active-member
checks will be implemented in the transactional services in Phase 3. No RLS or
authorization middleware is installed yet. Do not expose these tables directly to
the browser or treat this phase as a secure multi-tenant application launch.

Email keys must equal PostgreSQL `lower(btrim(email))`; API services must adopt this
same policy and validate email syntax. GSTIN/PAN constraints check normalized format,
not live registration or tax eligibility. One GSTIN per workspace is the initial
schema policy; different workspaces may represent the same registration.

Invites store a 64-character lowercase SHA-256 digest of a high-entropy token, never
the token itself. A partial unique index permits only one PENDING invite per
workspace/email. Expired invites still need their state changed before reissue;
future acceptance services must check time and role even if cleanup has not run.

All business foreign keys use RESTRICT: archive/suspend rather than cascading away
history. Audit triggers reject UPDATE, DELETE and TRUNCATE, and the table has no
updated timestamp. Privileged database owners can alter/disable triggers; this is
not tamper-proof storage. The normal application role must not own tables or have
DDL/TRUNCATE privileges, and should receive only SELECT/INSERT on audit events.

Audit JSON metadata is limited to a 16 KiB JSON object; run summaries to a 64 KiB
JSON object, measured as PostgreSQL's JSONB text representation. These are metadata
budgets, not capacities for invoice results. Secrets and financial source payloads
must be redacted/allowlisted by future audit services. `event_metadata` avoids the
SQLAlchemy-reserved attribute name `metadata`.

UUIDs are generated by application model defaults, not a database extension.
`created_at`/`updated_at` use timezone-aware timestamps and database creation
defaults. SQLAlchemy updates `updated_at`; raw SQL updates must explicitly maintain
it. Workflow checks validate known run statuses, nonnegative versions and terminal
timestamps, but a service must enforce the transition sequence.

## Install locally

Use Python 3.12. From the repository root in PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
$alignedDependencies = python -c "import pathlib,tomllib; print('\n'.join(tomllib.loads(pathlib.Path('pyproject.toml').read_text())['project']['dependencies']))"
python -m pip install $alignedDependencies
```

Use an installed Python 3.12 executable if the `py` launcher is unavailable.
The virtual environment is ignored by Git. The manifests specify compatible
version ranges; record resolved versions in deployment/CI qualification, rather
than upgrading production dependencies implicitly.

## Configure and migrate explicitly

See [safe environment examples](../.env.example). Neither FastAPI nor
Alembic automatically loads that file. Supply actual secrets via the shell or
deployment secret manager, not committed files or command transcripts.

- `DATABASE_URL`: application PostgreSQL credentials, `postgresql+psycopg` scheme.
- `MIGRATION_DATABASE_URL`: dedicated migration connection; Alembic falls back to
  `DATABASE_URL` when not supplied, but separate credentials are recommended.
- Production detection is `APP_ENV=production` or a truthy `VERCEL`. Production URLs
  must use `sslmode=verify-full`; configure the trusted CA required by the host.
- Default pool size is zero (`NullPool`); choose an external pooler or a small bounded
  application pool via `DB_POOL_SIZE`. A positive size has zero overflow. Do not
  multiply a large pool by serverless instance count.
- Connect, statement, lock and pool-wait timeouts have explicit configurable budgets.
  Statement/lock timeouts use libpq startup `options`. Verify that the selected
  managed pooler supports these before deployment; do not silently disable them.

With a dedicated development database configured:

```powershell
python -m alembic upgrade head
python -m alembic current
python -m alembic check
```

Review SQL without connecting or providing credentials:

```powershell
python -m alembic upgrade head --sql
```

Never call `create_all` or run Alembic on application startup or in a request.
Run migrations once as a reviewed release operation. Fresh connection/session
creation is opt-in; importing `backend.app.main` still works without a database URL.
`get_db_session` is available for future FastAPI dependencies; business services
must commit explicitly and avoid holding transactions during reconciliation,
exports or network calls. Errors roll back and sessions close.

The initial migration is frozen SQLAlchemy DDL, not an import of the live model
metadata. Its downgrade destroys these new tables and audit history: use it only
for disposable test/development databases. Back up and prefer forward fixes for
databases with real business data. No roles or databases are automatically created.

## Test on real PostgreSQL

Create an EMPTY disposable PostgreSQL database with a name ending in `_test` and
set `TEST_DATABASE_URL` through a secure environment. Never point it at production,
a development database with valuable data or a database shared with other tests.
The test fixture migrates it and downgrades/removes its own version table afterward.
It refuses an existing public-schema table or a non-default search path. Use one
test runner per database; these migration tests are not parallel-safe on a shared DB.

```powershell
python -m pytest backend/tests/test_database_config.py backend/tests/test_database_schema.py --require-postgres -q
python -m pytest backend/tests --require-postgres -q
python -m pip check
git diff --check
```

Without `TEST_DATABASE_URL`, the ordinary suite explicitly skips the PostgreSQL
tests. **That is not a database release pass.** The `--require-postgres` gate fails
when configuration is missing; a configured but unreachable/incorrect DB fails too.
SQLite is not used to emulate JSONB, partial indexes or composite constraints.

Tests cover both workspace types and mixed-type isolation, same-workspace/wrong-client
GSTIN links, membership/email/identity uniqueness, invite states/reissue, bounded
JSON, run versions, append-only audit behavior, safe connection configuration,
offline migration SQL, actual upgrade/downgrade and model/migration drift.

## Next backend phase

The updated [implementation plan](AUTH_DATABASE_IMPLEMENTATION_PLAN.md#10-backend-execution-plan-after-the-ui-preview)
proposes first-party credentials and server-side cookie sessions, then workspace
services. The first local authentication slice now connects sign-in/sign-up to
PostgreSQL; see [Local Auth Development](LOCAL_AUTH_DEVELOPMENT.md) for its limits.
Before exposing authenticated reconciliation,
every session/results/manual-match/export/status/delete route must check durable
workspace/client ownership. Existing anonymous Redis sessions are not automatically
owned by a newly created user. Connect the existing UI only to the implemented,
tested auth contract; keep production rollout gated on complete route protection.
